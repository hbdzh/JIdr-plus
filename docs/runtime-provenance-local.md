# Bundled runtime provenance — local candidate

Status: local verification in progress; **not approved for public redistribution**.

## Inputs

- Android Emulator `37.3.10`, build `16970787`, Google official archive `emulator-darwin_aarch64-16970787.zip`, SHA-1 `3ec739595d44092e835f006d806dd380bc8d6dd7`.
- Android SDK Platform-Tools `37.0.3`, Google official archive `platform-tools_r37.0.3-darwin.zip`, SHA-1 `d48920e2650321710b4d15d3acd9e277d59cd55b`.
- The official archives were downloaded and their archive checksums verified. Every file present in the candidate was compared to the matching archive entry: 200 emulator files match; the sole replaced file is `qemu/darwin-aarch64/qemu-system-aarch64-headless`. Its SHA-256 is `1731317391dcb943fc4dc867133045b75755b30e7ad49a9ca1b83ddbf88f7dbd`. Two `.miko-*` records are locally generated. All 12 platform-tools files match; its `.miko-package.json` is locally generated. Unused Qt and Android skin overlay APKs are absent from the candidate.
- The replacement was built locally from AOSP `platform/external/qemu` commit `5e51202879523d4df1bca8ca6944129ff05df02b`; six files are modified. The local diff SHA-256 is `342484fad499de73a48ad1604b5a14036a9c3a6025af2e5d990a292f7be04f2f`. The patch, observed project revisions, build-generated notices and pinned file hashes are retained in `packaging/runtime-source/`. A temporary source snapshot and dependency source candidates were also collected.
- The candidate copies upstream Emulator `LICENSE`, `NOTICE.txt`, `NOTICE.csv`, Platform-Tools `NOTICE.txt` and the locally generated core notices and licence texts with the binary files.

## Licence and source review

- The emulator notice identifies GPL-2.0-only QEMU, GPL-2.0-or-later FFmpeg and LGPL components among others. Its package root also includes an Apache-2.0 notice. Google SDK terms distinguish open-source components from other SDK components; the package cannot be treated as having one blanket licence.
- A source candidate was gathered for the modified QEMU tree and several identified dependencies. This is **not established to be the complete corresponding source** for every distributed binary. The QEMU patch and dependency source/revision mapping, build instructions, build-time dependencies, and source-offer/access method require verification.
- `libselinux` is labeled `CC-PDDC OR UNKNOWN` by the generated inventory; its source NOTICE states it is public-domain software with a warranty exclusion. Other component-level obligations still need review.
- The AOSP checkout's manifest export failed because the optional system-images project is absent. Existing project HEADs were recorded, but a clean rebuild and a fully pinned manifest are not yet verified. The locally built core is not currently reproducible by the repository's CI.
- Until the above review is completed, the conditional clean-room rule prohibits publicly redistributing the bundled candidate. This record is technical evidence, not a legal conclusion.

## Reproduction and verification performed

- `scripts/prepare-bundled-runtime.py` successfully reconstructed the 215-file pinned runtime from independently downloaded official archives, the saved metadata and the locally built core. The release command now rejects a missing, modified, additional or incomplete input before building.
- An ad-hoc local DMG built from the reconstructed runtime passed mounted-image validation, retained the original and generated core notices, and selected its embedded SDK from an isolated home. An isolated Android 36 device was created, started, stopped and deleted using the bundled runtime and a pre-existing read-only image.
- The final candidate, verified input archives and core, and the incomplete source-review kit are retained locally under `target/miko-runtime-review/`; this ignored directory is not a public source distribution or a long-term source offer.
- The published v0.10.0 tag and DMG predate this work and do not contain the runtime. The normal release command remains blocked pending review; The CI preparation action requires a separately supplied, reviewed pinned core and has not run on GitHub.

## Follow-up inspection — 2026-11-21

- The local headless core's Ninja link line includes static FFmpeg libraries and `libx264.a`; the link line alone does not prove which x264 objects were retained. Its FFmpeg `libavcodec` header reports version 58.134.100 and is byte-identical to FFmpeg 4.4.2. The generated runtime notices instead refer to FFmpeg 3.4.5, and do not list x264. These generated notices cannot be treated as a complete, accurate inventory of the modified core.
- Extracting the QEMU upstream source snapshot and applying `qemu-local.patch` succeeded; all six patched files match the local build tree byte for byte. This validates the saved QEMU delta, but is not a clean rebuild and does not establish the source for the stock binaries.
- AOSP's checked-out `PACKAGES.TXT` selects FFmpeg 4.4.2 and lists the x264 2017-01-03 snapshot; local source archives match its SHA-1 values. The installed x264 header matches that snapshot and identifies build 148. Both FFmpeg versions, x264, DTC and GLib candidates were added to `target/miko-runtime-review/source-review-v2-incomplete.tar.gz`. This is still **not a verified complete corresponding-source distribution**: the exact source and build instructions for Google's stock runtime binaries and all linked/prebuilt components remain unverified.
- The existing hosted workflow does not provision `MIKO_BUNDLED_SDK` or the patched core and therefore cannot build the required package. A clean AOSP rebuild has not been demonstrated: the local checkout occupies about 51 GiB and its build directory about 4.7 GiB, while [GitHub's standard macOS runners](https://docs.github.com/en/actions/reference/runners/github-hosted-runners) list 14 GB storage and 7 GB RAM. A suitably provisioned build environment or a separately reviewed, pinned core artifact is needed; do not publish an unreviewed core as a workflow artifact to work around the gate.
- The workflow output patterns and MCP download URL were corrected to match the actual `miko-simulator-*` and `miko-mcp-*` filenames. This correction does not configure runtime provisioning or lift the release gate.

## Source and automation work — 2026-11-21

The QEMU changes match the recorded patch. It does not establish correspondence for Google's stock binaries or identify every untracked build input.
- A fresh output-directory build from the existing source checkout succeeded after the checked-in Ninja directory was added to `PATH`. The rebuilt core's SHA-256 is `cc4b1b0a896b23761f44740dfe7e4235a962d2144754ae99e4a9145cac0fb501`, different from the pinned core `1731317391dcb943fc4dc867133045b75755b30e7ad49a9ca1b83ddbf88f7dbd`; their machine-code sections also differ. Both were separately exercised by booting and stopping an isolated Android 36 device, but this is not proof of functional equivalence or byte-reproducibility.
- The original Qt project's Git index has staged deletions for the whole project; its working tree is missing or differs on non-macOS platforms. A separate temporary index confirmed the macOS ARM64 Qt paths used by the build match their recorded commit. `scripts/build-runtime-core.py --verify-only` verifies the available tracked source, relevant macOS prebuilts and the recorded local SDK/linker configuration without changing that index. The full script was subsequently exercised end to end, as recorded below.
- The GitHub composite action for runtime preparation was simulated locally against independently verified archives. It accepted the pinned core and rejected an HTTP URL and a wrong core hash. It still requires a reviewed, stable HTTPS source for the core and has not run on GitHub; the public-release and artifact-upload gates remain closed.
- `NOTICE-build-addendum.txt` and the exact FFmpeg/x264 licence texts supplement, but do not replace, the original notices. Exact matching source, link-object retention, stock-binary provenance and a durable public corresponding-source mechanism are still open; the new material is not a completed distribution audit.

## Dependency archive and release workflow audit — 2026-11-21

- The pinned AOSP `prebuilts/android-emulator-build/archive/PACKAGES.TXT` has 46 active source entries. Of these, 37 URL archive entries match the recorded SHA-1 directly; the Qt 5.12.1 archive exists but does not match its listed checksum (`a06454758622c2c793caaec9f6e8e596569d56ea` versus `9377d37cdde14ba2009d4f2077986a8910d03ee7`). The Qt 6.2.1 archive does match; the local macOS arm64 Qt build script selects 6.2.1, but this alone does not establish all Qt binary provenance.
- The eight Git entries use AOSP's checksum of an extracted file list, not the archive-file checksum. All eight local archives, including `sccache`, match when checked using that algorithm; 45 of the 46 active source entries therefore match their listed checksum. The active x264 entry names a patch archive that is absent under that exact name; an archive with `-patches` in its name exists, but equivalence and application to the distributed static library have not been established. These are audit findings, not a claim that every listed dependency was linked into the release. `scripts/audit-runtime-dependencies.py` reproduces these archive and patch checks and correctly exits nonzero for both unresolved items.
- The release workflow now checks for a stable `vMAJOR.MINOR.PATCH` tag, checks out `refs/tags/` explicitly, and passes the tag through an environment variable instead of interpolating it into shell commands. The workflow has not been run on GitHub and the source-review and runtime-hosting gates are unchanged.

- Comparing printable strings in the old pinned core and the independent rebuild found two generated QAPI source paths containing their respective absolute output directories (`target/aosp-emulator-coreaudio` and `target/miko-core-repro-20261121`). Build location therefore affects the binary contents. This finding does not by itself explain every differing machine-code byte or prove functional equivalence.
- `scripts/build-runtime-core.py` completed all 5,513 build steps and verified the rebuilt core signature. The resulting SHA-256 was `f3fd5d07d632857f4ba531b74480c00a5c179049e4a37bc9ba713ad83be2bbda`, so the script correctly rejected it against the pinned `1731317391dcb943fc4dc867133045b75755b30e7ad49a9ca1b83ddbf88f7dbd`. This validates the build and rejection path in the existing checkout, not clean-room reproducibility or source completeness.

## Further inspection — 2026-11-21

- The checked-in Qt 5.12.1 archive has gzip format despite its `.tar.xz` name, which explains why the bytes do not match the listed upstream xz checksum; file content equivalence to the upstream xz was not established. The checked-in macOS ARM64 Qt prebuilt identifies itself as 6.5.3, not the 6.2.1 archive recorded in `PACKAGES.TXT`. The candidate runtime contains no Qt-named files, and `otool -L` shows no direct Qt dependency on the patched headless core; neither observation proves the absence of all indirect Qt-derived code.
- The available x264 `-patches.tar.xz` contains a single configure patch for Windows clang-cl cross-compilation, and it applies cleanly in a dry run to the recorded upstream x264 source. This narrows the patch naming discrepancy, but does not prove which inputs built the distributed x264 archive.
- A direct `NOTICE.csv` filename comparison identified seven of 45 emulator Mach-O files without a matching binary name (`crashpad_handler`, `libandroid-emu-base-logging.dylib`, `libimage_converter.dylib`, `libprotobuf.28.4.0.dylib`, `glslangValidator`, `mksdcard`, `netsimd`). This is only a filename-matching result, not a determination that a file lacks a license or notice; aliases and the full `NOTICE.txt` require individual review.
- The Release Please workflow now targets `master`, creates a draft release and a tag, and the packaging workflow publishes a draft only after artifact upload. Local mock tests passed for successful draft publication, an already-public release and failed-upload prevention. GitHub Actions run 44788669612 reached Release Please but failed: GitHub Actions was not permitted to create or approve pull requests; the packaging job was skipped. No release publication has been validated. The local runtime source review and public redistribution gate remain incomplete.

## Runtime notice inventory

- `scripts/inventory-runtime-notices.py` checked the original `NOTICE.csv` and every included emulator Mach-O file against the pinned SHA-256 manifest, then saved filename-based leads in `packaging/runtime-source/emulator-notice-inventory.json`. It records 45 Mach-O files, including the locally modified core, and seven files without an exact filename match in the notice CSV. An exact match is not proof that the notice is complete, that the binary corresponds to the linked source branch, or that all license obligations have been met. In particular, the upstream CSV predates the local core modification and contains identified FFmpeg/x264 omissions.
